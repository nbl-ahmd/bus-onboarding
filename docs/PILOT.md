# Pilot procedure

## Before passengers board

1. Use a trusted phone with sufficient battery, charging and storage.
2. Open the HTTPS production app while connected. Install from the browser if useful.
3. Confirm the fleet name, bus, actual route and overnight departure/arrival dates. Distance is omitted until entered. Add actual crew and stops.
4. Select Malayalam/English order. Confirm both scripts with a native Malayalam speaker.
5. Pair phone to the bus in OS settings and select Bluetooth on the head unit. Start at a low media volume and use the test tone. Walk to the rear to check clarity. A successful software playback alone proves nothing about cabin audio.
6. Upload recordings or prepare Gemini audio. Verify **Offline ready** for the exact script and language order. Review a complete announcement in both languages.
7. Disable mobile data temporarily and verify saved playback. Recheck before every departure and after changing facts.
8. Check what calls/notifications do on this specific phone/head unit. A personal phone shares its audio route with other apps.
9. Start the trip. Use while parked or let an attendant operate it. The ordinary PA microphone remains immediately available.

## During the trip

Configure the sequence once (for example EN → ML → EN → ML). Tap an announcement to play that full sequence. Use Edit or hold the row to change stop/delay fields or scripts first. Press Stop at any time. A changed stop, break duration, crew name, arrival or spoken script requires matching regenerated or recorded audio. If connectivity is absent, use an already-saved generic message rather than announce stale facts.

A congestion message uses only the reason selected by the crew. The system does not detect traffic, roadblocks or passenger return. A break timer is not a passenger headcount. Quiet mode displays a non-blocking night-journey note. An explicit manual tap never adds a confirmation. It is not an emergency system.

## At arrival

Select the actual drop-off, announce only once parked as appropriate, end the trip, and synchronize when connected. Review stopped/failed attempts and download activity if needed.

## Record pilot observations

- Phone model, OS, browser version, head-unit model and Bluetooth connection stability.
- Whether each language is clear throughout the cabin.
- Offline playback and reload after a weak-signal section.
- Behaviour after a call, navigation app, screen lock or Bluetooth reconnection.
- How many taps a driver/attendant needs for common moments.
- Whether overnight passengers find the number/timing of announcements useful.
- Incorrect facts, unclear Malayalam pronunciation, volume problems, duplicate playback or recovery issues.

Do not certify automation from this test: it evaluates the manual passenger experience and the actual audio connection. Cloud login, live Gemini and forecast behaviour require configured credentials and separate live checks.

Gesture checks: a hold must open editing without playing; scrolling must not start an announcement; a left swipe on the active player must stop remaining parts. The Stop button must work immediately, including between languages. Test both grouped and alternating sequences and save/reload the selected preset. Haptic behavior needs a real supported Android phone; browser tests only verify the feedback calls.
